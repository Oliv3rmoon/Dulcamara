# Native save maintenance

Eclipse keeps local snapshots in `backups/<game-id>/<snapshot-id>/`. A snapshot is visible only after its data and SHA-256 manifest have been checked and the directory has been renamed and its parent synchronized. Manual and recovery snapshots are retained. The five newest successfully published automatic snapshots share one retention budget, including early native checkpoints. An unchanged automatic snapshot reuses an existing verified snapshot; it does not require space for another full copy.

A GAME scope is an association, not an exclusivity guarantee. Persisted canonical layouts are compared across games for equal/ancestor overlaps, physical aliases and conservatively for case aliases. Exact shared files remain shared. Restore confirmation must show the resolved roots from the asynchronous DETAILS operation and explain that shared files can affect other games. Unregistered games or arbitrary Python I/O cannot be ruled out by this catalog.

## Native protocol v4

`src/core/runtime_protocol.h` is shared by all three cores and the host. The optional interface version is now 4. Unsupported clients can decline the extension and keep legacy native behavior; unsupported cores receive no backup eligibility. Rebuild all three archives and the frontend together. Version 4 adds kind5 without changing entry/layout size or the 32-entry bound. Unsupported older layouts/manifests/catalogs are retained and rejected; no automatic conversion broadens their historical scopes.

- `RPG_SLOTS` selects case-insensitive `Save*.lsd` in the declared native directory, including the engine's own archive save location. It never restores game assets.
- `FILE` selects exactly one native filename. MultiPersistent is always an exact shared FILE; its HOME parent is never expanded. Token declarations are exact shared `security_keys.txt` and `upgraded.txt` files from the native token resolver.
- `RENPY_SLOTS` selects direct regular-file children with the literal `renpy.savegame_suffix` supplied by the native producer, plus `persistent`, `persistent.new`, and the corresponding native `.new`/numeric `.tmp` artifacts. It can represent custom suffixes. Arbitrary neighboring scripts, assets and token files do not match this selector. The same matcher constrains capture, staging, deletion, rollback and recovery.
- `RENPY_FILE` (kind 5) selects one exact completed native filename plus only its `.new` and `.<ASCII digits>.tmp` siblings. This stable file-artifact selector never matches another slot, descendants, nonnumeric temporary names, or arbitrary neighboring persistent files. It remains one catalog entry across process timestamps and authorizes the same bounded family during capture, restore and pending-journal recovery. Ordinary `FILE` remains exact.
- The generic `DIRECTORY` kind remains available for explicit owned maintenance trees. The pinned RenPy adapters do not emit it. It must not be substituted for an unrepresentable native selector.

The shared Python helper resolves configured/local/extra locations before save initialization. `FileLocation.filename` re-declares its current native suffix before native operations; changes add another root/selector pair to the monotonic union. Old selectors are retained. An explicitly nested native slot operation adds one stable `RENPY_FILE` declaration; it does not authorize the parent or sibling descendants. Unobserved nested slots are not implied by a parent declaration. These declarations occur when `FileLocation.filename` is called. A call during python-early uses the existing preinitial barrier. A first call after initial release only expands the known layout: it does not establish global quiescence or retroactively add pre-play coverage. An already-existing nested slot first referenced during gameplay has no pre-write recovery copy from this launch; the clean post-stop snapshot captures its then-current bytes. The native regression exercises this gameplay-time declaration, post-stop restore, and preservation of unrelated descendants. The suffix is nonempty, at most 127 UTF-8 bytes, contains no path separators, and is not `.` or `..`. Roots are at most 1023 bytes and the union at most 32 entries. Invalid, overflowing or unsupported metadata fails protected discovery rather than widening scope. Custom Python I/O and native plugins outside these APIs are not covered.

`preinitial` is distinct from `initial`: it certifies only the currently declared native paths before a python-early native write. The host is still LOADING after its release. A snapshot of this partial union is labeled EARLY. `SaveRequest.session` identifies a launch, and `baseline` carries the prior successful early result, including an unchanged result from an earlier session. Subsequent early and full pre-play snapshots carry forward first-seen bytes and absence from that baseline. This preserves original coverage even if more than five early roots are declared. Baseline merging requires an actively held startup checkpoint, no finished writers, and an automatic kind; it is never applied to post-stop, manual or recovery capture.

Only the main thread calls host APIs. The service owns copies of request metadata. Main retains the exact generation and the service job serial until successful completion or explicit skip. Failure holds the checkpoint for retry/stop/skip. Stop during copying cancels the worker first; only then may native shutdown writers run. A timeout is sticky unsafe and never produces a snapshot. The runtime reservation remains held through post-clean-stop scheduling and completion, preventing a downloaded updater from overtaking protection. A failed post-stop operation also requires explicit retry/skip.

## UI service

`src/saves.h` supplies a single background job queue:

- `saves_init(root)` starts recovery. Launches remain locked until recovery succeeds.
- `saves_start(op, request, snapshot, confirmed)` copies its arguments. Operations are RECOVER, CREATE, RESTORE, DELETE, LIST, DETAILS and REGISTER. A manual CREATE with `layout.count == 0` uses the persisted native layout for that game. REGISTER persists association without taking a snapshot when automatic backups are disabled.
- `saves_start_page(game, offset)` lists a bounded page of 128 entries. `SavesStatus.count` is the total, `offset` the starting index; the populated count is `min(128, count-offset)`. Older retained manual snapshots remain reachable.
- DETAILS returns `detail` and `layout` asynchronously. Display these before supplying `confirmed=true` to RESTORE. `SaveInfo.moment` distinguishes EARLY, PREPLAY, POSTSTOP, MANUAL and RECOVERY. Label GAME roots “game-associated,” not “exclusive.”
- `saves_poll` copies coherent owned status, including job serial, phase, progress, result and errors. It joins only a completed worker. `saves_cancel` requests cancellation at safe boundaries. RESTORE rolls back if cancellation reaches apply; rollback itself is not cancellable.
- Main exposes `app_save_lifecycle_busy`, `app_save_failure_is_poststop`, `app_save_retry` and `app_save_skip_protection`. UI jobs must not replace a lifecycle-owned job. The main loop also checks the job serial and native checkpoint epoch, so stale success cannot release another startup hold.

The blocking `save_*` functions are worker/test interfaces, not UI-thread routines. Listing and details can hash and scan filesystem state. Final save screens, progress presentation and confirmation layout belong to Task5.

## Reusable transaction contract

`src/maintenance.h` owns the process-wide writer gate and blocking `mt_transaction` / `mt_recover` primitives. A caller acquires its owner before scheduling mutation and keeps it through recovery decisions. `maintenance_launch` atomically reserves the runtime before `host_load`; `maintenance_runtime` is a main-thread lifecycle publication, never a worker's inference from UI state. `maintenance_acquire(MAINT_UPDATE)` succeeds only after recovery and while no runtime or competing owner remains. Downloads may run independently. After installing an application, release with `restart_required=true`; launches then stay locked, while `maintenance_restart_ready` permits the required process restart.

Each `MtTarget` contains an explicit owned scope, canonical target, source (empty means deletion), and desired mode. Caller order is apply order; the updater puts its executable last. Sources are fully staged beside their destinations. Verified originals are retained in an exclusive journal directory, and original permissions survive rollback. Staged bytes, metadata, journal records and parent directories are synchronized before mutation. Space arithmetic is checked against actual filesystems, accounting conservatively for new and original bytes. Snapshot recovery copies consume space separately before restore staging is admitted.

The durable phase record includes a magic value and phase/complement validation. It is published before the immutable checked journal. PREPARING has not changed targets; APPLYING and ROLLBACK recover every original; COMMITTED is terminal cleanup. Recovery validates the entire journal, target scopes, counts, enums, digests, phase and all required original bytes before rolling back. Missing/corrupt phases, unauthorized targets, or incomplete directory enumeration retain records and lock launches. Snapshot, catalog, list, cleanup and recovery scans distinguish directory-read errors from end-of-directory immediately at each read. Repeated recovery is idempotent. Directory-rename publication makes interrupted snapshot deletion invisible to completed-snapshot listing.

Manifest and journal formats are version 2 and use bounded fixed-layout records on the supported little-endian PS5/macOS hosts; native layout version/size is checked. They are private storage formats, not a cross-version interchange API. Unsupported records are retained and rejected. All persisted bool flag bytes are validated before typed reads. Old completed snapshots are not discarded to make a failed write succeed. Recovery snapshots are not automatically deleted, including after a successful restore.

The updater supplies its app-owned scopes and invokes recovery for its own journal before allowing normal launches. Its staged installer uses these transactions and the shared maintenance gate/restart lock. The final packaged application and actual PS5 storage behavior still require Task8/hardware verification. Directory sync is mandatory: a filesystem that refuses it reports a failed operation and keeps existing data rather than claiming durability. Symlink traversal, special files, excessive paths/counts and storage errors fail safely. Hidden unpublished/deleting temporary directories from process termination are ignored; they may remain for conservative later cleanup.

## Eclipse transactional updates

Startup configures `maintenance_recovery_begin(MAINT_RECOVER_SAVES | MAINT_RECOVER_UPDATE)` before either subsystem can publish readiness. Main registers `update_recover_startup` with `saves_set_update_recovery` and resolves the installed application using `update_init`. The save worker recovers saves first, then invokes that narrow callback while it still owns `MAINT_RECOVERY`; the callback must not acquire the owner again. Each subsystem publishes only its own completion bit. A failed or not-yet-run callback leaves launches locked. Standalone save consumers retain the save-only default; production explicitly requires both.

Update recovery conservatively requires a process restart whenever its `.eclipse-update` workspace existed, including interrupted staging. It completes/removes the journal and workspace durably before success; the next process therefore does not repeat that restart. A failed recovery can retain a restart obligation. `MAINT_RECOVERY` remains acquirable while that obligation is set, but normal launches and all other mutation remain blocked. Restart readiness still requires every recovery bit. Explicit launch and restart-intent launch use the same gate. Main explains when recovery requires closing and reopening the process.

`update.c` owns checking/downloading and a mutex-protected `UpdateStatus` value. Workers copy version, URL, digest, expected size, data root and installation path before starting. UI polling receives coherent state/phase/message/progress; the legacy string accessors copy into main-thread-only buffers. Downloads and their existing range resume/retry/digest checks do not reserve maintenance. A downloaded update stays in WAITING until the runtime reservation and save operations finish. Staging/apply acquire `MAINT_UPDATE`; a stopped enum alone never authorizes it. The runtime reservation through post-stop backup/failure and sticky unsafe timeout is unchanged.

`update_storage.{h,c}` is the blocking installer/recovery boundary. It owns only `<installed-app>/.eclipse-update`, uses a dedicated payload directory and the shared transaction journal, rejects symlinks/special files, and verifies every archive member before replacement. ZIP names must start with exactly `PPSA99010/`; traversal, duplicate/case aliases, file/descendant collisions, reserved staging names, invalid local-header extents/overlaps and incomplete/corrupt content fail closed. Caller-authenticated ZIP SHA256 remains required. `eboot.bin` is the last transaction target; modules/executable retain executable permission. Unrelated installed files are preserved; no broad directory replacement or deletion of user data occurs.

Eclipse update ZIPs require `eclipse-payload.sha256`. Format v1 begins with `DULCAMARA-ECLIPSE-PAYLOAD-1\n`, followed by one lowercase SHA256, one decimal byte length and one relative UTF-8 filename per newline-terminated record, separated by single spaces. Every regular archive member except the manifest itself must occur exactly once, with no extra records. The manifest is at most 16 MiB; archive count is bounded by `MT_FILES_MAX`. `src/update_payload.h` supplies the required boot, both Ren'Py engine, UI and license anchors to both the installer and package generator. In addition to manifest hashes and ZIP CRCs, staged `sce_sys/param.json` must contain exactly one matching `titleId` and numeric `contentVersion` for the offered release. Codename/display text does not participate in version ordering.

`tools/update_payload.py <assembled PPSA99010 directory>` generates the manifest; both `tools/build.sh` and `tools/make_release.py` invoke it. Final release assembly **must regenerate it after inserting the complete Corresponding Source archive or changing any file**, then calculate the final ZIP SHA256. Task8 still owns that final assembly and delivery verification. Existing 0.2.x installed updaters simply copy the additional manifest file; they do not acquire transactional behavior retroactively. The Eclipse updater rejects packages without its complete manifest.

Free-space preflight checks the remaining ZIP download on the cache filesystem, then the actual installation filesystem against twice the entire expanded payload plus twice the replaced originals, bounded journal metadata and 16 MiB reserve, with checked arithmetic. This covers full extraction, adjacent transaction stages, rollback originals and rollback scratch. A large Corresponding Source member is counted in full; existing separate save-recovery copies already reduce reported free space. No retained backup is deleted to make an update fit.

Shared transactions retain journal version 2. Before any real staging they group target parents by filesystem device/inode and create exclusive zero-byte target/stage-name placeholders inside owned private probes. The filesystem itself decides name equivalence; this catches Unicode and normalization aliases without a guessed folding table. A checked `probe-plan` (private version 1, nonce and journal-record digest) is durable before the first probe directory is created. Recovery derives only its exact registered paths, accepts an empty interrupted first creation or matching partial owner marker, and requires the full nonce-bound marker before removing recognized zero-byte placeholders. Unknown content remains locked. Similarly named pre-existing directories are never scanned or removed.

The probe receipt distinguishes the initial pre-staging check from a check performed during recovery of already staged bytes. That distinction preserves original/stage cleanup after interruption of recovery itself. Failed initial checks retain their receipt until terminal phase and journal removal are durable; a terminal, journal-free receipt authorizes only metadata cleanup, never target or stage deletion. Probe cleanup errors leave one bounded recoverable plan, and retries synchronize removed paths before claiming success.

Shared transactions now reject stage/destination/source aliases in either target order before staging. Missing journals are accepted only with clean absence or validated terminal cleanup; surviving nonterminal phases/originals/unknown evidence remain locked. Directory enumeration errors never count as EOF. Recovery retries re-synchronize a supposedly absent workspace/empty transaction directory, so a previously failed final parent sync cannot be certified merely by observing that cleanup removed the pathname. Unknown or deliberately removed journal evidence is preserved for diagnosis, not guessed back into a safe state.

Unfinished cloud code is not integrated. A future cloud mutation must acquire the same maintenance owner, preserve worker-owned request metadata, and participate in startup completion if it adds durable recovery work; it must not publish an independent global ready flag.

Hidden workspace recovery uses a per-game `.cleanup-intent` beside snapshots. It binds the exact hidden basename, operation, game and filesystem device/inode; it is durable before creating an unpublished tree or renaming a verified completed snapshot for deletion. Creation records the exclusive directory identity before copying any save bytes. Recovery removes only the matching directory, flushes its absence, then clears and flushes the intent. A failed final flush is retried even when the target has disappeared. Visible completed snapshots are never selected by this cleanup.

Legacy hidden directories without an intent remain untouched and consume filesystem space. Changed inodes, symlinks, malformed records, or a non-regular `.cleanup-next` preserve evidence and block recovery for diagnosis. A regular `.cleanup-next` left by an interrupted record write is discarded: no workspace is created or renamed until that record has been renamed to `.cleanup-intent` and its directory flushed, so the unpublished slot never describes an action that happened. The fixed record slot prevents repeated ambiguous writes from creating an unbounded series of workspaces. The mkdir-to-identity gap allows only `rmdir` of the exact planned empty directory, never recursive deletion; nonempty uncertain data remains protected. Free-space admission uses actual filesystem availability including retained artifacts; listed snapshot payload sizes are not total disk usage.
