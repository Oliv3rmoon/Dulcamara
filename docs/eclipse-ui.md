# Eclipse controller interface

The existing shelf keeps Cross Play, Square Rescan (Cancel while scanning), Triangle Sort and Options Settings. L2 opens search, R2 opens filters and Touchpad opens details. Search reuses the game's keyboard model; Options accepts, Circle cancels, R1 clears, Square deletes a UTF-8 character. Held buttons, sticks and touches are withheld until released when changing screens.

Details uses an owned game descriptor while publication is held. Favorites are written before success is presented. Per-game preferences are sparse overrides: Left/Right changes a value; Square restores inheritance for that field. Controller mappings are independent per button. Global Settings remains separate from effective gameplay Settings, including when editing globals from an active game's menu. Keys and sound edits retain the previous effective value on persistence failure. Game details is also reachable from the gameplay menu.

Playtime counts foreground gameplay while the host is RUNNING, excluding loading, menus, background, save checkpoints and stopping. Last played is written at the first active running transition. Tiny profile/metadata/config writes use their checked persistence APIs; native snapshots/listing/details/restores remain on the save worker.

Backups show creation time, kind/moment, bytes and shared scope. L1/R1 navigates pages of 128 snapshots. Restore and deletion load details before confirmation, show game identity plus a separate date/type/size line and require release followed by a fresh Cross press. Completed-operation notices are cleared on confirmation; listing/details never announce mutation success. Up/Down scrolls declared save locations; L1/R1 scrolls long paths. Restore explains its pre-restore recovery copy and shared effects. Unsafe mutations are rejected with a reason. Circle cancels a confirmation or returns without waiting for a worker; Options requests safe cancellation while work is active. The v4 native scope/coverage limitations remain those documented in `save-maintenance.md`.

The lifecycle presents a transition frame before entering synchronous EasyRPG startup/stop boundaries. Those native intervals cannot remain interactive on the main thread. Save failures offer retry, stop and a separate explicit skip confirmation. A failed stop stays locked and says to close the process.

## Story mode

Settings > Library > View chooses Story (the default, `library_view = 0` in settings.ini) or the shelf (`1`), which is unchanged and is the fallback. Story (`src/ui/story.c`, words and timing in `src/ui/story_model.c`) draws the same state with a different pad mapping and owns none of it: the selection, sort, search, filters, rescan and Settings are the shelf's (`shelf_toggle_sort`, `shelf_square`, `library_view_select`, `panels_search`, `panels_filters`, `app_open_settings`), Favorite is the details panel's `panels_toggle_favorite`, Details is the details panel (`panels_details`, drawn as a status screen; Left/Right move through its actions as Up/Down do), Backups is the backups panel (`backup_panel_open_from`, drawn as save slots; Left/Right move through the slots), and Play is `app_start_game`. The backups panel's details read, release-then-press confirmation, Circle cancel, shared-location notes, recovery copy and job handling are unchanged; Story states them in its text box. Preferences, Keys, Sounds, search and filters open the existing panels. The launch transition's states and keys are main.c's; in Story view only its drawing is a chapter card while a game starts (stopping, a save-protection failure and an unsafe stop keep the existing frame).

The text box's line is cosmetic: it is typed out from elapsed time (no queue), any press shows it whole and still acts on that frame, and with Still background / reduced motion lines appear whole. The restore and delete questions are never typed, and a Cross in their first half second (the habit of pressing to see the text) answers nothing; a later, separate press confirms. The list draws only its visible rows; covers use the existing bounded path. The accent takes the hue of the chosen game's decoded cover (`covers_color`, averaged at decode time) and stays Eclipse red for dark or grey covers. Text in the window, list and text box uses DotGothic16 (`assets/fonts/DotGothic16-Regular.ttf`, OFL), with the Japanese subset for characters it lacks; long titles are cut with an ellipsis in the list and wrapped in the text box. Titles, folder names, paths and errors are plain text, never markup: Story marks each of their `{` (`story_plain`) so a title can neither become a pad glyph nor cut the line. The layout keeps the private-test mark's band (y 116-146) clear and the hint line at its usual place. Preview scripts can `assert view story|shelf` and `assert sort 0|1`.

## Generated skin and motion

`assets/ui/eclipse/` and `assets/backgrounds/` contain the selected ImageGen artwork and provenance. `src/ui/eclipse.c` decodes each image once into bounded working textures, uses measured crop/nine-slice regions, preserves square controller cells and caches a dedicated ten-glyph atlas. The renderer performs no subsequent image allocation, decode, texture creation or font rasterization. The animated plate, glyph drift, red trails, focus and status pulse use elapsed visual time; the clock does not advance in gameplay or while backgrounded. Global Settings > System > Still background / reduced motion persists the still option and stops interface easing too.

The frontend modules separate skin/motion (`eclipse`), controller state (`controller`), search/filter/details (`panels`), sparse profile editing (`preferences`), save jobs (`backup_panel`) and final composition (`watermark`). Existing keyboard, settings, About, community, insider, update and message surfaces share the skin primitives.

## Private test build mark

Normal builds omit the mark. For a test copy, set these variables at build time:

```sh
NP_PRIVATE_TEST=1 NP_TEST_RECIPIENT=Recipient NP_TEST_BUILD=review-001 bash tools/build-desktop.sh preview
```

The same variables are consumed by `tools/build.sh` for PS5 builds. Recipient is optional, up to 32 ASCII letters/digits/spaces/`._-`; build ID is required for a marked build, up to 20 ASCII letters/digits/`._-`. Other characters and incomplete configurations are rejected. `tools/gen-watermark.py` generates a C literal into the build directory; replacing its content invalidates the owning object through compiler header dependencies. CMake runs the generator on each build; the PS5 wrapper runs it before Ninja. Changing marked/unmarked, recipient or build ID therefore rebuilds the watermark input. There is no preference, telemetry or networking. Live text is drawn last over every screen, after games/dialogs/keyboard, without touching game pixels or saves. Final recipient/build metadata belongs to candidate assembly.

## Desktop evidence tooling

Build with `BUILD_JOBS=4 bash tools/build-desktop.sh preview`. Set `SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy NP_ROOT=<disposable-v4-root> NP_ASSETS=<repo>/assets NP_SCRIPT=<script> NP_SHOTS=<shots>` and run `build/desktop-preview/dulcamara`. Scripts use `wait`, `press`, `hold`, `shot`, `quit`; read-only `assert` checks screen, selected title, library game count, filter/query/favorite, effective/global/profile volume, still background, runtime/save state and backup confirmation. They do not change application state.

Only NP_PREVIEW accepts navigation-only `fixture renpy-menu`, `fixture keyboard`, `fixture insider`, `fixture update`, `fixture update-progress`, `fixture update-failed`, `fixture update-installed`, `fixture message` and `fixture off`. These explicitly labeled offline fixtures use the production renderers, disable writes/install side effects and do not represent real service offers or Ren'Py desktop execution. Production/PS5 does not compile the fixture controls. Actual EasyRPG gameplay, and real Ren'Py native headless tests, are separate evidence.

Preview visual/game clocks are fixed 60 Hz. `preview real costs` uses SDL's host performance counter for draw/present and input-poll cost; `preview real main` separately measures complete loop work and input-to-present, including synchronous transition work in full-frame cost. Neither is console pacing. Run matched motion-on/off scenes serially after warmup, without captures, builds or tests competing for resources. Hardware and final updater transaction integration remain separate validation gates.
